# ADR-DI-001: 自建 DI 容器而非使用 shaku 框架

## 状态
- [x] 已接受
- [ ] 已废弃
- [ ] 已替代

## 背景 (Context)

### 问题描述
Workflow Toolkit 需要一个依赖注入（DI）容器来管理组件的生命周期和依赖关系。当前 `src/di/container.rs` 是占位实现，需要决定是继续完善自建方案还是引入成熟的 DI 框架。

### 约束条件
- 必须支持异步服务初始化
- 必须支持单例和工厂两种注册模式
- 必须线程安全，支持并发访问
- 不能引入过多的外部依赖
- 需要支持模块化配置和依赖拓扑排序

### 影响范围
- `src/di/` - DI 容器核心实现
- `src/di/modules/` - 模块配置
- 所有需要依赖注入的服务组件

## 决策 (Decision)

### 选择的方案
**继续使用自建 DI 容器**，不引入 shaku 或其他第三方 DI 框架。

### 决策理由
自建方案已满足当前需求，且具有更好的灵活性和可控性。

## 选项对比 (Options Considered)

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **自建 DI 容器** (已选择) | 完全可控、无额外依赖、可定制化、学习成本低 | 需要自行维护、功能相对简单 | ✅ 选择 |
| shaku | 功能完善、编译时检查、社区支持 | 学习曲线陡峭、宏语法复杂、异步支持有限 | ❌ 不选 |
| wait_di | 轻量级、异步原生 | 社区小、文档少、维护不稳定 | ❌ 不选 |
| teloc | 简单易用、零成本抽象 | 功能有限、不支持复杂依赖图 | ❌ 不选 |

## 详细分析

### 1. 自建 DI 容器

**当前实现状态**:
```rust
pub struct DiContainer {
    singletons: RwLock<HashMap<TypeId, Arc<dyn Any + Send + Sync>>>,
    factories: RwLock<HashMap<TypeId, ServiceFactory>>,
    resolved: RwLock<HashMap<TypeId, Arc<dyn Any + Send + Sync>>>,
}
```

**已实现功能**:
- ✅ 单例注册和解析
- ✅ 工厂方法注册
- ✅ 线程安全（RwLock 保护）
- ✅ 服务缓存
- ✅ 错误处理

**待完善功能**:
- 🔄 带依赖的工厂方法（当前实现有缺陷）
- 🔄 模块系统（AppModule trait）
- 🔄 依赖拓扑排序
- 🔄 生命周期钩子

### 2. shaku 框架

**优点**:
- 编译时依赖检查，避免运行时错误
- 宏驱动的声明式配置
- 支持多个组件实现同一接口

**缺点**:
- 宏语法学习曲线陡峭
- 异步初始化支持有限
- 与现有代码集成需要大量重构
- 编译时间增加

## 影响 (Consequences)

### 正面影响
- ✅ 完全掌控 DI 实现，可根据需求灵活调整
- ✅ 无额外依赖，减少供应链风险
- ✅ 团队无需学习新框架，降低认知负担
- ✅ 与现有代码无缝集成

### 负面影响/风险
- ⚠️ 需要自行维护和测试 → 增加单元测试覆盖率
- ⚠️ 功能可能不如成熟框架完善 → 按需迭代，不过度设计
- ⚠️ 循环依赖检测需要手动实现 → 实现依赖拓扑排序算法

### 技术债务
- 带依赖的工厂方法实现有缺陷 → P1 阶段已修复
- 缺少模块系统 → P1 阶段已实现 AppModule trait
