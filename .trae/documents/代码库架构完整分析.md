# Workflow Toolkit 代码库架构完整分析

## 1. 项目概述

### 1.1 基本信息

| 项目属性 | 描述 |
|---------|------|
| **项目名称** | Workflow Toolkit |
| **版本** | 0.1.0 |
| **语言** | Rust (Edition 2021) |
| **描述** | 基于 Rust 的多接口工作流执行系统 |
| **许可证** | MIT |

### 1.2 核心特性

- **多接口支持**: CLI、TUI、MCP Server 三种交互方式
- **DDD 分层架构**: 领域驱动设计，清晰的职责分离
- **多类型插件**: Native、Python、Node.js、Docker、WASM
- **工作流引擎**: LiteFlow 风格的组件 + 执行器链架构
- **容错机制**: 检查点、熔断器、重试策略

---

## 2. 架构分层

### 2.1 DDD 四层架构

```
┌─────────────────────────────────────────────────────────────┐
│                      接口层 (Interfaces)                      │
│         CLI        TUI        MCP Server                     │
│    用户交互入口，处理请求/响应转换                              │
└──────────────────────────┬──────────────────────────────────┘
                           │ 依赖
┌──────────────────────────▼──────────────────────────────────┐
│                    应用层 (Application)                       │
│         UseCase    Service    Workflow Orchestration         │
│    用例编排、事务管理、应用服务                                 │
└──────────────────────────┬──────────────────────────────────┘
                           │ 依赖
┌──────────────────────────▼──────────────────────────────────┐
│                    领域层 (Domain)                            │
│         Model      Port (Repository/Service Interface)       │
│    业务逻辑、领域模型、端口定义                                 │
└──────────────────────────┬──────────────────────────────────┘
                           │ 被依赖
┌──────────────────────────▼──────────────────────────────────┐
│                  基础设施层 (Infrastructure)                  │
│    Persistence   Plugin   Cache   External   Config          │
│    技术实现、持久化、外部服务集成                               │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 模块依赖关系

```
interfaces → application → domain ← infrastructure
                ↓              ↑
            workflow ←→ tools ←→ plugins
                ↓              ↓
            storage ←→ performance
```

**依赖规则**:
- 依赖方向: interfaces → application → domain ← infrastructure
- 领域层不依赖任何其他层
- 基础设施层实现领域层定义的 Port

## 3. 核心模块详解

### 3.1 领域层 (Domain)

**路径**: `src/domain/`

**职责**: 系统核心，包含业务逻辑和领域模型，不依赖其他任何层。

#### 模块结构

```
domain/
├── model/              # 领域模型
│   ├── workflow.rs        # 工作流实体
│   ├── execution.rs       # 执行实体
│   ├── tool.rs            # 工具实体
│   ├── plugin.rs          # 插件实体
│   └── value_object.rs    # 值对象
└── port/               # 端口定义
    ├── repository.rs      # 仓储接口
    ├── tool_registry.rs   # 工具注册表接口
    └── plugin_manager.rs  # 插件管理器接口
```

#### 核心领域模型

| 实体 | 职责 | 关键属性 |
|------|------|---------|
| `WorkflowDefinition` | 工作流定义（聚合根） | id, name, nodes, edges, config |
| `WorkflowExecution` | 执行记录（聚合根） | id, workflow_id, status, context |
| `ToolInfo` | 工具定义 | name, version, input/output schema |
| `PluginInfo` | 插件信息 | name, type, metadata |

#### 端口定义

```rust
// 仓储接口
pub trait WorkflowRepository: Send + Sync { ... }
pub trait ExecutionRepository: Send + Sync { ... }

// 工具注册表接口
pub trait ToolRegistry: Send + Sync { ... }

// 插件管理器接口
pub trait PluginManager: Send + Sync { ... }
```

### 3.5 工作流引擎 (Workflow)

**路径**: `src/workflow/`

**职责**: 工作流定义、验证、调度和执行。

#### 模块结构

```
workflow/
├── definition.rs       # 工作流定义
├── engine.rs           # 引擎实现
├── execution.rs        # 执行状态管理
├── execution_manager.rs # 执行管理器
├── scheduler.rs        # DAG 调度器
├── validator.rs        # 验证器
├── audit.rs            # 审计日志
├── result_cache.rs     # 结果缓存
├── circuit_breaker.rs  # 熔断器
├── rate_limiter.rs     # 限流器
├── component/          # 组件系统
│   ├── tool.rs         # 工具组件
│   └── parallel.rs     # 并行组件
├── context/            # 数据上下文
│   └── slot.rs         # 数据槽
├── executor/           # 执行器链
│   ├── basic.rs        # 基础执行器
│   ├── retry.rs        # 重试执行器
│   ├── cache.rs        # 缓存执行器
│   └── audit.rs        # 审计执行器
└── state/              # 状态管理
    └── checkpoint.rs   # 检查点
```

#### 架构风格

采用 **LiteFlow 风格**的组件 + 执行器链架构：

```
请求 → [审计执行器] → [缓存执行器] → [重试执行器] → [基础执行器] → 响应
```

#### 核心组件

| 组件 | 职责 |
|------|------|
| `DefaultWorkflowEngine` | 主执行引擎 |
| `DagScheduler` | DAG 调度和依赖解析 |
| `ExecutionManager` | 执行生命周期管理 |
| `CheckpointManager` | 检查点保存和恢复 |
| `CircuitBreaker` | 熔断保护 |
| `RateLimiter` | 限流控制 |

## 5. 架构决策记录 (ADR)

### ADR-001: DDD 分层架构
- **决策**: 采用 DDD 四层架构
- **理由**: 清晰的职责分离，便于测试和维护
- **风险**: 初期开发成本较高

### ADR-002: Tokio 异步运行时
- **决策**: 使用 Tokio 作为异步运行时
- **理由**: 生态成熟，性能优秀
- **风险**: 学习曲线较陡

### ADR-003: 错误处理策略
- **决策**: thiserror + anyhow 组合
- **理由**: thiserror 定义错误类型，anyhow 简化应用代码
- **风险**: 需要团队统一规范

### ADR-004: LiteFlow 风格引擎
- **决策**: 组件 + 执行器链架构
- **理由**: 更好的扩展性，支持 AOP 风格横切关注点
- **风险**: 学习成本

### ADR-005: Enum-based 工具系统
- **决策**: 从 trait-based 重构为 Enum-based
- **理由**: 更好的性能，更简单的序列化
- **风险**: 扩展性稍差

### ADR-006: 进程级插件隔离
- **决策**: 进程隔离 + 资源限制
- **理由**: 安全性优先
- **风险**: 启动开销，使用进程池优化

## 6. 执行流程

### 6.1 工作流执行流程

```
1. 接收 WorkflowDefinition（工作流定义）
2. 验证定义（validator）
   ├── DAG 结构验证
   ├── 节点存在性验证
   └── 工具可用性验证
3. DAG 调度（scheduler）
   └── 拓扑排序 + 分层执行
4. 初始化执行上下文
5. 按层执行节点：
   a. 获取可执行节点
   b. 并行执行（max_concurrent 限制）
   c. 执行器链处理（retry/cache/audit）
   d. 更新执行状态
   e. 保存检查点（如启用）
6. 返回执行结果
```

### 6.2 插件生命周期

```
1. 配置验证
2. 运行时准备（进程池）
3. 插件加载
4. 初始化调用
5. 工具执行（多次）
6. 关闭调用
7. 资源清理
```

## 11. 总结

### 11.1 架构优势

1. **清晰的分层**: DDD 四层架构确保职责分离
2. **高扩展性**: 插件系统支持多种技术栈
3. **容错能力**: 检查点、熔断器、重试机制完善
4. **多接口支持**: CLI/TUI/MCP 满足不同场景
5. **可观测性**: 完善的日志、指标、追踪支持

### 11.2 技术亮点

1. **Enum-based 工具系统**: 性能优于传统 trait 方案
2. **执行器链模式**: AOP 风格的横切关注点处理
3. **进程级插件隔离**: 安全可靠的外部代码执行
4. **LiteFlow 风格引擎**: 灵活的工作流编排

### 11.3 改进建议
