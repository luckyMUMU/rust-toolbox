# 工具系统架构重构计划 (Tool System Architecture Redesign Plan) v2

根据单一职责原则 (SRP) 和您的具体要求，我制定了以下重构和增强计划。

## 1. 架构设计原则与规范 (Architecture Design & Standards)

### 1.1 工具设计规范 (SRP)
- **单一职责**: 每个工具仅执行一个原子操作（如 "读取文件"、"正则匹配"、"移动文件"）。
- **无状态/纯函数**: 工具应尽量设计为无状态，输入参数决定输出结果，不依赖隐含的外部状态。
- **命名规范**: `VerbObject` 或 `NounAction` 形式，如 `FileScanner`, `DataValidator`, `JsonTransformer`。
- **逻辑剥离**: 复杂的业务流程（如“如果文件大于10MB则压缩否则直接移动”）移至 **Workflow** 层通过编排实现，禁止在工具内部写 `if/else` 处理业务逻辑。

### 1.2 新增核心节点类型 (New Node Types)
我们将通过特殊的 **系统工具 (System Tools)** 来实现这些节点功能，保持架构的一致性：

1.  **DataCacheNode (数据暂存节点)**
    *   **实现**: `DataCacheTool`
    *   **功能**: 在 `ExecutionContext` 或 `StateManager` 中读写键值对。
    *   **操作**: `set(key, value, scope)`, `get(key)`, `clear(key)`.
    *   **用途**: 跨节点传递非直接依赖的数据，保存中间计算结果。

2.  **TransformNode (数据转换节点)**
    *   **实现**: `DataTransformTool`
    *   **功能**: 对输入数据进行结构转换、类型映射或格式化。
    *   **操作**: `map(input, schema)`, `convert(input, format)`, `jq(input, filter)`.
    *   **用途**: 适配不同工具间的输入输出格式（如 XML -> JSON）。

## 2. Workflow 系统增强 (Workflow System Enhancement)

### 2.1 条件分支逻辑实现 (Conditional Branching)
目前 `DagScheduler` 仅支持静态依赖。我们将增强引擎以支持动态流控制：

*   **Edge Conditions**: 利用 `WorkflowEdge` 现有的 `condition` 字段（支持简单表达式，如 `${prev.result.score} > 0.8`）。
*   **运行时评估**: 在节点执行完成后，评估其出边 (Outgoing Edges) 的条件。
*   **跳过逻辑 (Skip Logic)**:
    *   如果条件为 `false`，则标记目标节点状态为 `Skipped`。
    *   `Skipped` 状态会级联传播：依赖于 `Skipped` 节点的后续节点也将被标记为 `Skipped`（除非有其他活跃路径）。

### 2.2 数据流增强
*   **上下文增强**: 确保 `ExecutionContext` 在节点间正确传递，并支持 `DataCacheTool` 的读写。

## 3. 实施步骤 (Implementation Steps)

### 阶段 1: 规范文档化 (Standards Documentation)
1.  **创建 `docs/TOOL_DESIGN_STANDARDS.md`**: 详细定义工具开发的 SRP 原则、命名规范、接口要求及反模式示例。
2.  **更新 `AGENTS.md`**: 增加对 `TOOL_DESIGN_STANDARDS.md` 的引用，要求 AI 助手在生成新工具时严格遵守此规范。

### 阶段 2: 核心工具开发 (Core Tools Implementation)
3.  **实现 `DataCacheTool`**: 支持基于 `ExecutionContext` 的数据存取。
4.  **实现 `DataTransformTool`**: 集成简单的模板引擎或 JSON 转换逻辑。

### 阶段 3: 引擎升级 (Engine Upgrade)
5.  **增强 `DefaultWorkflowEngine`**:
    *   引入 `eval_condition(condition, context)` 函数。
    *   在 `scheduler` 中处理条件判断结果。
    *   实现 `mark_node_skipped` 及其传播逻辑。

### 阶段 4: 现有工具重构 (Refactoring)
6.  **拆解 `folder-classifier`**:
    *   `DirectoryScanner`: 扫描目录 -> 文件列表。
    *   `RuleMatcher`: 文件 + 规则 -> 分类结果。
    *   `ActionPlanner`: 分类结果 -> 移动/复制指令。
    *   `FileMover`: 执行指令（纯粹执行）。
7.  **重写 Workflow**: 使用新的原子工具和条件边重新组合“交互式文件分类”工作流。

### 阶段 5: 辅助工具开发 (Auxiliary Tools)
8.  **Workflow Debugger**: 在 CLI 中增加 `--debug` 模式。
9.  **Performance Profiler**: 增强 `AuditLogger` 记录性能指标。

我将优先执行 **阶段 1** 和 **阶段 2**，确保规范先行，基础工具就绪。
