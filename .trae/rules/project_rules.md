# Rust 工具箱项目规约 (Project Specific v5.3)

**项目定位**：高性能、跨平台 Rust 异步工具集
**技术底座**：Rust 1.70+ / Tokio 异步体系 / 强类型安全

---

## 2. 核心架构与依赖拓扑 (Architecture)

本项目严格遵循以下**单向依赖模型**，严禁逆向引用：

1. **`rt-core` (基础层)**：
* **职责**：定义核心领域模型、通用 Trait、配置管理、日志系统、插件接口、持久化协议等基础组件。
* **约束**：**零外部业务依赖**，禁止引用其他业务模块。


2. **`rt-tools` (内置工具层)**：
* **职责**：内置工具的具体实现（如文件操作、文本处理等）。
* **约束**：仅依赖 `rt-core`，通过 Trait 实现具体功能。


3. **插件系统**：
* **职责**：外部扩展工具，包括拼音处理、YouTube 下载、文件清理等。
* **模块**：`rt-plugin-pinyin`、`rt-plugin-ytdlp`、`rt-plugin-czkawka` 等。
* **约束**：仅依赖 `rt-core`，通过插件接口与系统交互。


4. **`rt-cli` & `rt-gui` (交互层)**：
* **职责**：命令行与图形界面的入口分发，用户交互处理。
* **约束**：依赖 `rt-core` 和 `rt-tools`，仅负责数据展示与交互，**禁止编写核心业务逻辑**。

## 3. 项目特有的实现规范 (Implementation)

### 3.1 异步与并发特选

* **文件操作**：统一使用 `tokio::fs`，禁止在 `async` 函数中使用 `std::fs`。
* **通道通信**：模块间解耦优先使用 `tokio::sync::mpsc` 或 `broadcast`。

### 3.2 错误域设计

* **统一 Error**：各模块必须定义自己的 `Error` 枚举，并使用 `thiserror` 库进行派生，确保错误信息在核心逻辑与交互层间透明传递。

### 3.3 模块化设计示例

* 当在 `rt-tools/src/parser/` 下新增解析逻辑时，必须在对应的 `design.md` 中说明该解析器如何适配 `rt-core` 定义的 `Parser` Trait。

## 4. 目录结构与文档分布

AI 应当根据此结构定位 `design.md` 并执行公共规约中的设计流程：

```text

├── .trae/            # Trae IDE 配置

├── rt-plugin-pinyin/  # 拼音处理插件
├── rt-plugin-ytdlp/   # YouTube 下载插件
├── rt-tools/         # 内置工具实现层 (包含 design.md)
└── design.md         # 根目录设计文档

```

## 5. AI 执行上下文补全

当执行公共规则中的“任务拆分”时，AI 需额外检查：

* **兼容性**：新功能是否同时适配了 `rt-cli` 和 `rt-gui`？
* **Trait 约束**：是否优先复用了 `rt-core` 中的抽象接口？
* **插件架构**：新增功能是否适合作为内置工具（rt-tools）或外部插件？
* **PowerShell 适配**：生成的 CLI 示例命令是否已转义 PowerShell 特殊字符（如 `${}` 或反引号）。
* **国际化**：新增工具是否包含多语言支持（locales 目录下的翻译文件）？
